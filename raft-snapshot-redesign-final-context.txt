1. ORIGINAL TASK AND ACCEPTANCE CRITERIA
================================================================================
  "Review and redesign Hazelcast Raft snapshot generation to eliminate
   data-size-dependent pauses and latency spikes across the ENTIRE snapshot
   lifecycle, including writing the generated snapshot to disk."
  Hard requirements (all still standing):
    - the Raft thread performs only BOUNDED coordination (O(1)-ish);
    - data traversal / serialization / chunking / disk I/O run OFF the Raft
      thread;
    - no data-size-dependent pauses on the Raft thread (generation AND disk
      persistence);
    - log truncation only after durable publish;
    - bounded memory / bounded disk / bounded retained log;
    - bounded queues + backpressure (new appends rejected when the pipeline
      cannot keep up);
    - bounded completion/failure callbacks;
    - robust failure handling (retry, no lost state);
    - full compatibility with the existing chunked snapshot protocol
      (InstallSnapshot, ChunkedSnapshotInstaller, followers, membership
      changes);
    - tests/benchmarks reporting p50/p95/p99/max of Raft-operation latency.

2. DESIGN HISTORY AND THE CHOSEN ARCHITECTURE
================================================================================
  Explored options (all documented in the raft-*.txt files, section 12):
    A  async full snapshot (COW freeze; had an O(container) first-write hole)
    B  WAL + incremental delta emission into a durable block store
    C  rqlite-informed (FSM snapshot + chunk pipeline, MRSW staging reuse)
    D  SQLite-backed RaftStateStore
    E  etcd-informed (two-tier memory/disk snapshot cadence, bbolt read-tx)
    F  versioned state; HAMT proposed and REJECTED (per-op O(log n) apply is
       unacceptable) -> CHM + O(1) delta emission + transient shadow freeze
  CHOSEN: Option F (the synthesis). Key ideas, all now implemented:
    (1) O(1) per-op delta emission at the SERVICE BOUNDARY (no generic SPI;
        a CPMap-internal store decorator).
    (2) O(1) capture via a transient WRITE-REDIRECTION FREEZE (shadow/overlay)
        so the O(n) scan can run off-thread at a single point-in-time.
    (3) The O(n) chunked scan + chunk building + disk persistence run on a
        bounded snapshot WORKER; the Raft thread only does capture (O(1)),
        the bounded install (log.setSnapshot + truncate) and bounded
        callbacks.
    (4) A durable DELTA TIER (append-only delta log + durable snapshot index
        S advanced only after fsync = group commit) feeding crash/restart
        recovery; the chunked full snapshot remains the transfer/install tier
        (lagging followers and joiners still need the full state).
    (5) Three thread domains (documented as design section 3):
        Domain 1 partition (Raft) threads  — O(1) coordination only;
        Domain 2 snapshot worker pool       — node-wide, bounded (global task
                                              scheduler in the impl);
        Domain 3 store I/O (optional)       — inside the store impl.

3. FINAL ARCHITECTURE (implemented, property-gated)
================================================================================
  ENABLED BY: -Dhazelcast.cp.snapshot.enabled=true (default OFF; when off,
  every change is provably behavior-neutral — verified by the test suite).

  A) DELTA EMISSION (the O(1) per-op path)
     applyLogEntry -> DeltaContext (ThreadLocal) -> store decorator emits
     key-level DeltaRecord{s} into a bounded per-group sink. Restore/install
     never opens a context, so it never emits.

  B) TRANSIENT FREEZE (the O(1) capture)
     - SnapshotShadow: standalone map-level freeze (worker copies `main`,
       drains overlay, single-writer flips when empty).
     - SnapshotOverlay: the EXTERNAL-main variant used by CPMapRegistry
       (one overlay per registry, composite key CPMapShadowKey(map,key) so
       the registry snapshot is atomic ACROSS maps). While active, all store
       mutations redirect to the overlay and the real stores stay frozen;
       finish() applies the overlay back on the Raft thread (single writer,
       so no update can be lost).

  C) ASYNC CHUNKED GENERATION (kills the O(n)-on-Raft-thread problem)
     takeSnapshotIfCommitIndexAdvanced:
       capture = raftIntegration.captureSnapshot(commitIndex)   // O(1)
       if capture != null -> takeSnapshotAsynchronously(...):
           worker executes: takeCapturedServiceSnapshots (frozen scan)
                            -> createChunksFromSnapshot -> persistAndFlush
                            -> submit(installChunkedSnapshot)
           Raft thread (completion): compute truncation index,
                            log.setSnapshot, finishSnapshotCapture (release).
       if capture == null -> the ORIGINAL synchronous path (unchanged).
     Small services (atomic refs etc.) are captured synchronously in
     captureSnapshot (bounded, not data-size-dependent).

  D) DURABLE TIERS
     - FileRaftStateStore: members/term (atomic rename+fsync), append-only
       length-prefixed raft log (torn-tail tolerant), snapshot chunks staged
       and atomically published on flushLogs; implements RaftStateLoader
       (load() -> RestoredRaftState) for restart restore.
     - FileIncrementalSnapshotStore + IncrementalSnapshotStore interface:
       append-only delta log + durable-s.dat; S advances ONLY after fsync
       (group commit). Un-flushed tails stay replayable after a crash.

  E) PIPELINE COORDINATOR
     SnapshotPipeline: beginApply(opIndex) opens the context; onApplied()
     submits ONE drain (in-flight=1 coalescing) to the worker; drain appends
     deltas to the durable store + flush; completion/failure callbacks are
     routed back to the Raft thread via raftIntegration.submit; on failure
     the drained records are re-queued (never lost) and retried.

5. WIRING / INTEGRATION POINTS (exact)
================================================================================
  - RaftNodeImpl.applyLogEntry: when snapshotPipeline != null ->
    try (DeltaContext ctx = pipeline.beginApply(index)) { runOperation } ;
    pipeline.onApplied(). Else the original single call (byte-identical).
  - RaftNodeImpl.initSnapshotPipeline(): factory + worker from the
    integration; notifiers = () -> raftIntegration.submit(...) so callbacks
    run on the group's partition thread (happens-before preserved).
  - NodeEngineRaftIntegration.snapshotDir / RaftService.raftStateStoreDir:
    <root>/<localMemberUuid>/... per-member scoping (critical for same-JVM
    multi-member tests; also the correct real-cluster shape).
  - RaftService.createRaftNode: FileRaftStateStore when enabled, else the
    enterprise CPPersistenceService store (unchanged default).
  - CPMapService.getOrInitMapStore: wraps stores with the decorator (+overlay)
    when enabled; capture/finish delegate to the registry overlay.
  - CPMapRegistry: overlay redirect happens inside the decorator's put/pia/
    cas/remove/get (overlay-then-store); finish() applies the overlay to the
    real stores with CPMapStore.NO_TIMESTAMP (purge timestamps are a
    documented limitation, see section 9).

6. MEMORY BOUNDS AND BACKPRESSURE (the "will it OOM?" answer)
================================================================================
  - Raft log: FIXED-CAPACITY ringbuffer (~cadence 10000 + uncommitted 100 +
    keep-after-snapshot 1000 = ~11100 entries). RaftLog.appendEntries throws
    IllegalStateException when full -> the append is rejected, the client
    retries. The log cannot grow without bound.
  - Uncommitted entries: canReplicateNewEntry rejects at maxUncommittedEntryCount
    (default 100).
  - In-flight overlay + delta sink during the async window: grow only from
    APPLIED writes, which stop when the log fills -> implicitly bounded by the
    ringbuffer capacity.
  - NEWLY WIRED explicit cap: SnapshotPipelineConfig.maxSnapshotLag =
    cadence x multiplier (default 4; property hazelcast.cp.snapshot.lag.multiplier,
    0 disables). canReplicateNewEntry rejects appends when
    commitIndex - snapshotIndex > maxSnapshotLag (only when the feature is
    enabled). Failure mode = bounded append stall with client retry, never OOM.
  - Worst-case memory during a long async window: roughly doubles (log entries
    + overlay/delta copies of the same writes), bounded by the lag cap.

7. KEY INVARIANTS (the subtle parts a reviewer must verify)
================================================================================
  I1  Raft thread does no O(size) snapshot work: capture O(1), install bounded
      (O(members)+O(logCapacity)), callbacks bounded.
  I2  The async scan reads the FROZEN state at the CAPTURED commit index; the
      snapshot must not contain ops beyond that index (the overlay redirect
      guarantees this).
  I3  Overlay finish runs on the single-writer (Raft) thread -> no update can
      be lost (the F8-style invariant is trivially satisfied: capture and
      finish are both on the same thread).
  I4  Delta emission only with an active DeltaContext (apply); restore/install
      never emits.
  I5  durable S advances only after the delta log is fsync'd (group commit) —
      the anchor of "truncate only after durable publish".
  I6  Torn-tail tolerance: a crash mid-write leaves a partial trailing record
      that is silently dropped on load (raft log and delta log).
  I7  Per-member directory scoping (same-UUID members must not share store
      files — this bug broke leader election in the smoke test and was fixed).
  I8  Property OFF => behavior-neutral: the async branch is skipped (capture
      returns null), the decorator is not wired, the lag cap is not checked,
      the store is the enterprise one. Proven by LocalRaftTest 27/27 and
      CPMapRegistrySnapshotTest 1/1.

9. REMAINING SCOPE (documented follow-ups, not omissions)
================================================================================

      on the delta store's durable S needs membership metadata carried in the
      incremental store; today the chunked snapshot still drives truncation.
  R2  OSS restart-restore: no restore loop exists in OSS RaftService (the

      implements the RaftStateLoader contract and is ready for that hook.

11. REVIEW CHECKLIST (what to scrutinize)
================================================================================
  [ ] applyLogEntry context wrap is strictly additive (pipeline == null ->
      original single call) — confirm byte-identical behavior.
  [ ] Async generation: the snapshot is built from the state AT THE CAPTURED
      index (overlay freeze), and the install uses the captured term/index,
      not the current ones.
  [ ] canReplicateNewEntry lag-cap check is skipped when the feature is off,
      and cannot fire during normal operation (cap = 4x cadence).
  [ ] SnapshotOverlay.finish on the Raft thread: no concurrent writes can
      interleave -> the F8 no-lost-update invariant holds trivially.
  [ ] Delta sink failure path re-queues drained records (never lost) and the
      failure notifier runs on the Raft thread via submit.
  [ ] Worker = the node-wide global task scheduler: check for contention with
      raft timers/heartbeats under load (a dedicated bounded pool may be
      preferable; documented as a tunable).
  [ ] FileRaftStateStore crash semantics: atomic rename + fsync for metadata
      and snapshot publication; torn-tail tolerance on both logs.
  [ ] Per-member directory scoping is applied in BOTH RaftService (raft-state)
      and NodeEngineRaftIntegration (delta).
  [ ] The 3 pre-existing ChunkedSnapshotInstallerTest failures are baseline
      (git-stash verified) and unrelated.
  [ ] The property-on cluster test (AsyncChunkedSnapshotTest) exercises the
      async path end-to-end; consider extending it to assert the lag-cap
      rejection and follower-install after a full async cycle.
